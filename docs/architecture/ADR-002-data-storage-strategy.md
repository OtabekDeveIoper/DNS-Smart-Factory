# ADR-002: Data Storage Strategy

## Status

Accepted

## Context

DNS Smart Factory MES manages several types of data with different consistency,
volume, query, retention, and storage requirements.

The system contains:

- transactional manufacturing data;
- high-frequency equipment telemetry;
- temporary cache and background job state;
- images, drawings, reports, and certificates;
- AI inference inputs and outputs.

Using one storage technology for every data type would create unnecessary
performance, reliability, and operational problems.

## Decision

The system will use four storage categories:

- PostgreSQL for transactional MES data;
- TimescaleDB for time-series and equipment telemetry;
- Redis for ephemeral state, cache, queues, and locks;
- S3-compatible object storage for binary files.

Each storage technology has an explicit ownership boundary.

## PostgreSQL

PostgreSQL is the authoritative source of truth for transactional MES data.

It stores:

- organizations, plants, lines, work centers, and equipment;
- users, roles, permissions, and plant memberships;
- products, revisions, BOMs, and routings;
- sales orders, work orders, units, and operations;
- inventory lots, reservations, and stock transactions;
- inspections, measurements, NCRs, and CAPA actions;
- audit logs;
- AI job metadata and inference results;
- integration state, inbound messages, and outbox events.

Changes to related business entities must be committed in a single PostgreSQL
transaction where atomic consistency is required.

Core MES records must never depend on Redis or TimescaleDB being available to
remain valid.

## TimescaleDB

TimescaleDB is used only for time-series workloads.

It stores:

- equipment telemetry;
- equipment state changes;
- energy meter readings;
- environmental measurements;
- downtime signals;
- raw OEE signals.

Transactional entities such as work orders, inventory balances, inspection
approvals, and user permissions must not be stored as TimescaleDB telemetry.

TimescaleDB will initially run as an extension in the same PostgreSQL database
infrastructure. It can be moved to a separate database when telemetry volume,
retention, or scaling requirements justify the operational cost.

Hypertables, continuous aggregates, compression, and retention policies are
created through version-controlled SQL migrations.

Prisma may represent the base telemetry tables when useful, but
TimescaleDB-specific policies and continuous aggregates are managed through
SQL migrations and parameterized SQL repositories.

## Telemetry Retention

The initial retention targets are:

- raw telemetry: 90 days;
- one-minute aggregates: 12 months;
- hourly and shift aggregates: 3 years;
- daily manufacturing KPIs: 7 years.

These values are deployment policies, not hard-coded application constants.

Retention and continuous-aggregate refresh windows must be configured together
to prevent historical aggregates from being unintentionally deleted.

Telemetry timestamps are stored in UTC using `timestamptz`.

Every telemetry event includes a source message ID to support deduplication.

## Redis

Redis is not a source of truth.

Redis is used for:

- BullMQ job queues;
- short-lived cache;
- distributed locks;
- API rate limiting;
- WebSocket scale-out;
- idempotency locks;
- short-lived session or token revocation state.

Every cache entry must have a TTL.

The application must remain correct after Redis cache data is removed.

Cache invalidation occurs after the related PostgreSQL transaction commits.

A distributed lock must have a bounded expiration time and an ownership token.

Important queue jobs must be reconstructable from PostgreSQL state or the
transactional outbox.

## Object Storage

S3-compatible object storage is used for:

- inspection images;
- AI input images;
- product drawings;
- work instructions;
- generated reports;
- test certificates;
- exported files.

Buckets are private.

Clients access files through short-lived pre-signed URLs generated by the API.

PostgreSQL stores file metadata including:

- object key;
- original file name;
- content type;
- byte size;
- checksum;
- owner entity type and ID;
- uploaded-by user ID;
- created timestamp.

Database records store object keys, never permanent public URLs.

Large binary files must not be stored directly in PostgreSQL or Redis.

## AI Data

AI inspection images are stored in object storage.

PostgreSQL stores:

- AI job status;
- provider and model;
- prompt version;
- image checksum and object key;
- structured prediction;
- token usage;
- latency;
- estimated cost;
- human review;
- final inspection decision.

OpenAI responses are not treated as the final quality decision.

The final decision is stored only after the configured human-review workflow.

## Consistency

PostgreSQL transactions provide strong consistency for core MES commands.

External side effects use the transactional outbox pattern.

The expected flow is:

1. validate the business command;
2. update core MES records;
3. write audit and outbox records in the same transaction;
4. commit the transaction;
5. let the worker dispatch the outbox event;
6. update cache and notify WebSocket clients.

Telemetry ingestion is eventually consistent with operational dashboards.

## Backup and Recovery

PostgreSQL requires automated backups and tested restore procedures.

Object storage requires versioning or lifecycle-based backup where available.

Redis queue persistence is configured, but Redis backup does not replace
PostgreSQL recovery.

TimescaleDB backup is included in the PostgreSQL backup strategy while it
shares the same database infrastructure.

A backup is not considered valid until a restore test succeeds.

## Security

Database and Redis ports are not publicly exposed.

Connections use authentication and encryption where supported.

Object-storage credentials are available only to the API and worker.

Sensitive manufacturing files are never placed in public buckets.

Production secrets are stored outside the Git repository.

## Consequences

### Benefits

- Each data type uses storage suited to its access pattern.
- Core manufacturing transactions remain strongly consistent.
- Telemetry can scale independently when required.
- Redis failures do not corrupt authoritative MES data.
- Large binary files do not increase transactional database size.

### Trade-offs

- Operations must monitor multiple storage systems.
- Cross-storage workflows require explicit consistency handling.
- Cache invalidation and retention policies require tests.
- Backup and disaster-recovery procedures become more detailed.

## Rejected Alternatives

### PostgreSQL for All Binary Files

Rejected because large images and documents would increase database size,
backup duration, and query overhead.

### Redis as Authoritative State

Rejected because cache eviction or Redis failure must not lose MES records.

### TimescaleDB for All MES Data

Rejected because transactional MES data and high-frequency telemetry have
different consistency and query requirements.

### Separate Telemetry Database from the First Release

Rejected because the current telemetry volume does not justify additional
deployment and operational complexity.
