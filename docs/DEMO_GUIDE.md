# SMART OPS 데모 가이드

## 목표

- 전체 시간: 약 6분
- 핵심 메시지: 단순 대시보드가 아니라, 제조 데이터를 연결해 납기·재고·품질 의사결정을 지원하는 운영형 MVP
- 원칙: 화면의 숫자를 모두 읽지 말고, 각 화면이 해결하는 문제와 데이터 흐름을 설명한다.

## 시연 전 체크리스트

```bash
docker compose ps
curl http://localhost:3000/api/health
```

- API: `http://localhost:3000/api`
- Web: `http://localhost:3001`
- Swagger: `http://localhost:3000/api/docs`
- 브라우저 언어는 `KO`, 첫 화면은 `통합 관제`로 맞춘다.
- AI 검사 버튼과 API가 정상 동작하는지 시연 전에 한 번 확인한다.

## 0:00–0:35 | 문제와 목표

**화면:** 통합 관제

> 안녕하세요. 이 프로젝트는 수배전반 제조 현장의 수주, 생산, 검사, 재고, 품질 이력을 하나로 연결한 SMART OPS 데모입니다.
>
> 현장에서는 납기 위험, 자재 부족, 시험 이력이 서로 다른 문서와 사람의 경험에 분산되기 쉽습니다. 저는 이 데이터를 호기 단위로 연결하고, 문제가 발생한 뒤 확인하는 것이 아니라 납기와 결품 위험을 미리 계산하는 운영형 MVP를 구현했습니다.

**전달 포인트**

- 수주부터 품질 이력까지 하나의 흐름으로 연결했다.
- 예쁜 화면보다 사전 의사결정 지원이 목적이다.

## 0:35–1:05 | 아키텍처

**화면:** 통합 관제 유지

> 프론트엔드는 Next.js와 SWR, 백엔드는 NestJS, 데이터베이스는 PostgreSQL과 Prisma로 구성했습니다. 모노레포 안에서 Web, API, DB 패키지의 책임을 분리했습니다.
>
> 화면은 REST API를 통해 데이터를 조회하고, 운영 지표는 15초 또는 30초 주기로 갱신합니다. 현재 과제 범위에서는 안정적인 REST polling을 선택했고, 긴급 이벤트가 필요한 운영 환경에서는 WebSocket과 MQTT를 단계적으로 추가할 수 있도록 도메인 경계를 분리했습니다.

**전달 포인트**

- 기술 이름만 나열하지 말고 각 기술의 역할을 한 문장으로 설명한다.
- WebSocket과 MQTT가 현재 구현되어 있다고 말하지 않는다.

## 1:05–1:50 | 통합 관제

**동작:** KPI, 라인 현황, 주간 실적, 실시간 알림을 순서대로 가리킨다.

> 통합 관제에서는 금일 실적, 진행 호기, 납기준수율, 재작업, 설비 가동률을 한 번에 확인할 수 있습니다.
>
> 아래 라인 현황은 공정별 완료 건수와 상태를 보여 줍니다. 특정 공정이 지연되면 이후 공정과 납기에 어떤 영향을 주는지 빠르게 파악할 수 있습니다. 오른쪽 알림은 납기 위험, 자재 부족, 검사 이상과 같은 이벤트를 심각도와 함께 보여 줍니다.
>
> 이 값들은 프론트에 고정한 숫자가 아니라 seed 데이터와 현재 시각을 기준으로 API에서 계산한 결과입니다.

**전달 포인트**

- KPI가 DB 집계 결과라는 점을 강조한다.
- 현재 시간에 따라 납기 수치가 달라질 수 있음을 알고 있어야 한다.

## 1:50–2:40 | 수주·공정과 납기 역산

**동작:** `수주·공정 진척` 탭 클릭 → 위험 상태 행 → 하단 계산 설명

> 수주·공정 화면에서는 수주번호별 진행률, 현재 공정, 납기 상태를 확인합니다.
>
> 핵심은 하단의 납기 역산 로직입니다. 각 호기의 잔여 표준공수 중 가장 큰 값을 기준으로 생산 소요일을 계산하고, 수주별 버퍼를 더해 필요한 일수를 구합니다. 이후 납기까지 남은 일수와 비교해 정상, 지연주의, 납기위험으로 분류합니다.
>
> 즉, 작업자가 경험으로 판단하던 위험을 동일한 기준으로 반복 계산할 수 있습니다. 실제 운영에서는 근무일 캘린더, 인력, 설비 능력을 추가해 정밀도를 높일 수 있습니다.

**공식**

```text
productionDays = remainingStandardHours / 8
requiredDays   = productionDays + bufferDays
marginDays     = availableDays - requiredDays
```

## 2:40–3:40 | AI 배선검사

**동작:** `AI 배선검사` 탭 클릭 → 호기 선택 → `AI 검사 실행 (시연)` 클릭 → 결과와 검사 이력 확인

> AI 배선검사는 작업자가 호기를 선택하고 촬영했다고 가정한 시연입니다. 실행하면 프론트가 검사 API를 호출하고, 백엔드는 판정 결과와 신뢰도, 결함 위치를 저장합니다.
>
> 결함이 감지되면 검사 레코드뿐 아니라 실시간 알림용 이벤트도 같은 트랜잭션에서 생성합니다. 그래서 검사 결과가 대시보드 알림과 호기별 품질 이력에 연결됩니다.
>
> 이번 과제에는 실제 비전 모델을 포함하지 않았고 판정 결과는 mock입니다. 대신 대상 조회, 검사 실행, DB 저장, 이력 재조회까지 실제 서비스 흐름을 구현했습니다. 실제 모델을 연결할 때는 이 API 경계를 유지한 채 추론 adapter만 교체할 수 있습니다.

**전달 포인트**

- 실제 AI 모델이라고 과장하지 않는다.
- mock은 판정 엔진이며, API와 저장 흐름은 실제 구현이라고 구분한다.

## 3:40–4:30 | 자재·재고

**동작:** `자재·재고` 탭 클릭 → 부족 카드 → 발주 제안 테이블

> 자재 화면은 현재고만 보여 주는 것이 아니라, 미완료 호기와 BOM을 기준으로 향후 2주 수요를 계산합니다.
>
> 단위당 소요량에 잔여 호기 수와 불량 여유율을 반영하고, 안전재고까지 포함해 부족 수량을 구합니다. 리드타임은 납기일이 아니라 생산 착수 예정일에서 역산해 발주 필요일을 계산합니다.
>
> 따라서 구매 담당자는 어떤 자재가 얼마나 부족한지뿐 아니라 언제까지 발주해야 하는지 확인할 수 있습니다.

**공식**

```text
twoWeekDemand = remainingUnits × quantityPerUnit × (1 + scrapRate / 100)
requiredStock = twoWeekDemand + safetyStock
shortage      = max(requiredStock - currentStock, 0)
purchaseByAt  = earliestRequiredAt - leadTimeDays
```

## 4:30–5:20 | 시험·품질 이력

**동작:** `시험·품질이력` 탭 클릭 → 수주 선택 → 시험표 → Traceability 흐름

> 품질 화면에서는 절연저항, 내전압, 동작시험의 측정값과 기준, 판정 결과를 확인할 수 있습니다.
>
> 아래 Traceability는 수주번호 하나를 기준으로 수주 정보, 자재 LOT, 생산 공정, AI 검사, 시험, 성적서까지 연결합니다. 발주처 문의나 클레임이 들어왔을 때 여러 문서를 찾지 않고 동일한 이력을 조회하는 것이 목표입니다.
>
> 이 구조는 향후 호기 명판의 QR 코드와 연결해 유지보수와 개보수 이력으로 확장할 수 있습니다.

## 5:20–5:45 | 다국어와 안정성

**동작:** 우측 상단 `EN` 클릭 후 한 화면 확인 → 다시 `KO`

> UI는 한국어와 영어를 지원합니다. 단순 문자열 교체가 아니라 날짜, 숫자, 단수·복수 형식도 locale에 맞게 처리했고 선택 언어는 브라우저에 저장됩니다.
>
> API 오류에는 공통 loading, error, retry 상태를 적용해 일시적인 장애에서도 사용자가 복구할 수 있도록 했습니다.

## 5:45–6:05 | 마무리

> 정리하면, 이 MVP는 수주부터 품질까지 제조 데이터를 연결하고 납기와 자재 위험을 사전에 계산하는 데 집중했습니다.
>
> 실제 운영 확장 시에는 OPC-UA 또는 MQTT 수집 adapter, 긴급 이벤트용 WebSocket, 인증과 권한, 근무일 기반 스케줄링을 우선 추가하겠습니다. 감사합니다.

## 시연 중 장애 대응

### API가 내려간 경우

1. 화면의 error/retry UX를 설명한다.
2. API 터미널을 확인하고 `npm run dev:api`를 재실행한다.
3. `다시 시도`를 클릭한다.

### AI 검사 요청이 실패한 경우

1. 기존 검사 이력을 먼저 보여 준다.
2. Swagger의 `POST /api/inspections/analyze` endpoint를 설명한다.
3. 데모 전체를 멈추지 않고 품질 추적으로 이동한다.

### 데이터 수치가 예상과 다른 경우

> 납기 위험과 금일 KPI는 현재 시각을 기준으로 계산되므로 seed 시점과 실행 시점에 따라 값이 달라질 수 있습니다.

## 반드시 구분해서 말할 것

| 항목        | 현재 구현                    | 확장 방향                      |
| ----------- | ---------------------------- | ------------------------------ |
| AI 판정     | Mock 판정 + 실제 API/DB 저장 | 실제 vision model adapter      |
| 실시간 갱신 | SWR 15~30초 polling          | WebSocket event push           |
| 설비 연동   | UI와 도메인 구조             | OPC-UA/MQTT adapter            |
| 시계열 저장 | PostgreSQL 업무 데이터       | 고주기 센서에 TimescaleDB 검토 |
| 운영 보안   | MVP 범위 밖                  | 인증, RBAC, 감사 로그          |

## 연습 방법

1. 첫 연습은 문서를 보며 8분 안에 끝낸다.
2. 두 번째 연습은 각 섹션의 첫 문장만 보고 7분 안에 끝낸다.
3. 세 번째 연습은 화면만 보며 6분 안에 끝낸다.
4. 숫자를 외우지 말고 공식과 데이터 흐름을 설명한다.
